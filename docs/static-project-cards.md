# 作品カードの静的化方針

## 現在の設計

作品名・説明・リンクを、JavaScriptを実行しない環境でも初期HTMLから読み取れるようにする。
ゲーム4件、ツール5件、メモ・記録2件の計11件のカードをindex.htmlに直接記述している。作品情報の唯一の管理先はindex.htmlであり、JSONとHTMLを二重管理しない。

app.jsはフッターの年号更新のみを行う。カード生成・データ取得・alert()による取得エラー表示はなく、移行元のassets/data.jsonは削除済み。ビルド工程やnpm依存関係は不要。

通常カードはモバイル2列・md以上3列・xl以上4列で表示する。新しい作業予定は[改善TODO](task-list.md)で管理する。

## 採用方式と理由

index.htmlにカードを直接記述する。現在の小規模な一覧では、生成スクリプトや公開工程を増やすよりHTMLだけで管理する方が単純であり、作品情報も初期HTMLに含められる。既存のGitHub Pages向け静的構成を維持する。

## 採用時の方式比較（移行時は10件）

| 観点 | index.htmlへの直接記述 | data.jsonからビルド時にHTML生成 |
| --- | --- | --- |
| 管理しやすさ | HTML編集が必要だが、10件なら更新箇所を把握しやすい | データはJSONに集約できるが、生成手順が必要 |
| SEO | 作品情報が初期HTMLに存在する | 生成済みHTMLを公開すれば同じ条件を満たせる |
| GitHub Pagesとの相性 | 既存の静的ファイルとして配信できる | 生成物の管理または公開前の生成工程が必要 |
| 保守性 | テンプレートの繰り返しはあるが、依存関係とビルド処理が増えない | カードの共通化は容易だが、生成スクリプトと実行環境の保守が増える |

## 現在の作品追加・更新手順

カードの追加・更新、画像とaltの扱い、年号初期値の更新、変更記録の更新方法は[READMEのコンテンツの追加・更新](../README.md#コンテンツの追加更新)を参照する。運用手順の管理先はREADMEとし、この文書では重複して記載しない。

設計上、作品情報の唯一の管理先はindex.htmlとする。削除済みのassets/data.jsonを再作成せず、更新のためにビルド工程を追加する必要はない。

## 公開構成

ユーザーの共有事項により、このリポジトリはGitHub Pagesで公開されている。ルートにindex.html、styles.css、app.js、assetsがあり、CNAMEはrutile3.comを指定する。公開URLは[https://rutile3.com/](https://rutile3.com/)。

GitHub側の公開元ブランチ・ディレクトリ・デプロイ方式・独自ドメイン設定の詳細は、この文書では未確認。ローカルの構成だけから公開設定を推測しない。設定の調査が必要な場合はSettings → Pagesが参照先になるが、現在の必須タスクには含めない。

## 移行の記録

既存10件をJavaScript生成から静的HTMLへ移行し、生成・取得・alert処理とassets/data.jsonを削除した。その後Tab Link Exporterを追加し、現在は11件となっている。実施内容と当時の確認結果は[仕様変更](spec_changes.md)と[追加仕様](spec_additions.md)に記録している。
