# rutile3.com 改善TODO

## 方針

作品掲載・構成改善・保守の未完了タスクを管理する。新しい作業はブランチ単位で整理し、その中の作業をコミット単位で記載する。

- タスク番号とコミット番号で作業を指定できる。削除済みの完了タスクの番号は、新しい作業に再利用しない。
- 各タスクにブランチ名とコミットごとの対応範囲・メッセージ案を記載する。コミットメッセージは「【概要】説明」の形式にする。
- 各コミットに必要な変更記録とTODOの進捗更新を含める。コード変更はAGENTS.mdに従い日本語で記録する。
- 表示・リンク・公開状態の確認専用タスクは追加しない。編集時の書式チェックと、対象コード・文書の読み取りは行う。
- 既存作品の情報・リンク先・OGP・Google Analytics・静的HTML構成を維持する。今回依頼された作品追加のみ、必要最小限の表示変更を行う。
- 完了項目は関連文書への反映後にTODOから削除する。履歴は変更記録とGitで管理する。
- devへの集約運用は検討段階。今回のTODO作成ではブランチ・公開設定を変更せず、採用決定前に文書へ確定手順として記載しない。

### 掲載に共通する方針

- 各掲載ブランチのコミット1で、作品のタイトル・紹介文・主要機能・技術的な工夫・リンク先・画像方針をdocs/project-content.mdに記録する（未作成なら追加する）。作品別の見出しで管理し、根拠となるREADME・実装等のURLを残す。
- 情報源の読み取りは紹介文を作成する作業の一部とし、確認だけのブランチや表示・公開確認タスクを追加しない。ユーザー提供情報と外部ソースで確定した情報を区別し、取得できない点は未確定として記録する。
- 紹介は短い用途説明を中心に、主要機能・技術・設計を補足する。ユーザーが挙げた要素が伝わるよう整理し、すべてを長い1文に詰め込まない。開発者向けの詳細は短い補足や成果物のREADMEへ案内する。
- 実在する素材を使う。適切な画像がなければ画像なしのカードを選択できる。架空の画像パス・配布ページ・ストア掲載URLを設定しない。画像生成が必要な場合は別途方針を決め、アクセス範囲のルールに従う。
- 初期HTMLに情報を記述し、JavaScriptによるカード生成・新しいビルド工程は導入しない。追加カードの書式・alt方針・外部リンク属性は既存ルールに合わせる。
- 各コミットにTODOの進捗を反映する。掲載のコード変更はdocs/spec_additions.mdへ記録し、既存構成の変更はdocs/spec_changes.mdへ記録する。対象外の既存作品は変更しない。
